## 决策一：检索与分发架构（静态 / 重排 / RAG）

### 选项 0：纯静态精选（craft-library.md 只收 25-35 条，无检索机制）

- **机制**：建库时人工把 ~76 条 CR 论断筛到 25-35 条核心，按 CL-<分支>-xx 登记；
  任务时路由判分支 → grep 工艺库对应节 → 全文进上下文。没有运行时选择逻辑。
- **优点**：零基建、零依赖、完全可审计（每条在册、grep 即得）；上下文成本确定
  （每任务最多读一个分支节，几百 token）；与现有治理（指纹/④a④b）无缝。
- **缺点**：召回靠建库时的人工判断——筛掉的那 40 条中，某些任务恰好需要时**系统性
  静默缺失**（agent 不知道库里没有的那条存在）；扩建要人手重排全表。
- **失效模式**：条目涨到 ~50+ 后单分支节超上下文舒适区；或任务类型分化（人像 vs
  产品 vs 风光同为 A 分支但需要的条目子集不同）——静态全读开始浪费/挤占上下文。
- **适用判断**：当前 76 条 CR 合并后 ~55 条，筛到 30 条会扔掉约 45% 的收料——
  **可接受但可惜**；适合作为"过渡形态"而非终态。

### 选项 1：静态清单项库 + 模型重排（推荐）

- **机制**：两层结构。**第一层=craft-library.md 清单项**（同选项 0 的精选，
  每任务必读、必遵守）；**第二层=craft-research/ CR 池**（原样保留，带稳定 ID）。
  运行时流程（全在当前 harness 内，无新基建）：
  1. 路由判分支（现有第 0 步）；
  2. 读该分支清单项（同选项 0）；
  3. **重排步**：按任务特征（人像/产品/风光；印刷/网页；单张/批量）对本分支
     CR 块打分排序，取 top 3-5 条作"参考候选"进上下文——标注"候选，非强制"；
  4. 任务收工三问时，若某候选被实战验证，晋升清单项并留出处（现有纪律）。
- **打分 rubric（重排步用）**：任务特征匹配度（话术/文件特征命中）> 证据强度
  （官方/权威/多源）> 新鲜度（时效敏感条目降权）> 冲突状态（争议条目只呈现不裁决）。
- **优点**：召回与成本解耦（池子随便涨，上下文只进 top-k）；无基建（我就是重排器）；
  池子格式已 RAG-ready，未来可平移；候选晋升有实战数据兜底，不污染清单项。
- **缺点**：重排质量依赖当次任务的上下文理解（rubric 写不细会漂）；每次多花一次
  模型读池子的成本（一个分支节 ~1-2k token，可接受）；可审计性比静态弱——
  "为什么这条候选被带进上下文"需要在 report/开工消息里留痕（重排步的 top-k 与理由
  进开工消息，可审计）。
- **失效模式与切换阈值**：CR 池 >200 条或分支 >10 个时，运行时读池变贵 → 升选项 2；
  出现"重排漏掉关键条目导致实战错误"≥2 次 → 说明 rubric 不够，先改 rubric 再考虑 2。

### 选项 2：向量 RAG 知识库

- **机制**：CR 块（已是天然 chunk：单句论断+ID+来源）→ embedding → 向量库
  （本机 sqlite-vec/FAISS，或现成 MCP memory 服务）→ 任务时语义检索 top-k。
- **优点**：真正的语义召回（话术无关的任务也能命中）；规模上限最高；跨 skill
  共享一个库（blender/达芬奇家族可共用）。
- **缺点**：**当前规模下是负优化**——76 块的检索收益 < 基建+维护成本（embedding
  生成、库运维、检索质量评估、失败调试链）；路由第 0 步（判分支）已经是最强语义
  过滤器，RAG 在它之后只做"分支内 10-20 条里选 5 条"——这个粒度模型重排（选项 1）
  就够，向量检索的区分度优势体现不出来；多一层"检索不到"的静默失败面（正是本系列
  最警惕的家族）。
- **切换阈值（三选一满足即重评）**：CR 池 >200 块；家族多 skill 共享工艺语料；
  选项 1 的重排连续漏检（rubric 修订后仍 ≥2 次）。

### 决策一默认建议：**选项 1**，分两步走——先按选项 0 建"清单项层"（本周内可完成），
CR 池原样保留即自动获得选项 1 的第二层；重排步作为运行时纪律写进 00 分册（不写代码）。
向量 RAG 挂"切换阈值"待办，不预建。

## 决策二：X 跨分支条目的编码

背景：~11 条 CR-X（无损纪律/色彩导出/图层命名/停手/披露/多方案）跨分支适用，
但路由分支码只有 A-H。

- **选项 a：新增 CL-X-xx**，00 分册路由后果加一条"**所有任务都读 X 节**"。
  优点：不拆散跨分支语义（这些条目的本质就是"不论什么任务都适用"）；一处维护。
  缺点：每任务多读一节（~11 条，几百 token，可接受）；X 与 A-H 并列后"分支"概念
  被稀释（X 不是路由去向，是附加层）。
- **选项 b：拆回各分支**（每条 X 论断复制/改写到适用的分支节）。
  优点：任务时只读一个节；概念纯净。缺点：同一论断多分支重复（CR-X-03 色彩红线
  在 A/C/D 三分支都要），修订要多处同步——**修订传导家族的隐患**，与治理纪律相抵。
- **选项 c：只登记 A-H，X 论断升格进 SKILL 铁律/门**（凡"所有任务都适用"的，
  本质是铁律级，放 SKILL 而非工艺库）。
  优点：语义最诚实——CR-X-01/02/07/08 确实够铁律格。缺点：升格要逐条裁决（不是
  所有 X 条都够铁律级，如 CR-X-11 只是好习惯）；SKILL.md 的 500 行红线压力。

### 决策二默认建议：**选项 a（CL-X-xx）+ 选项 c 混合**——X 节先收全部跨分支候选；
建库时逐条审一遍，够格升 SKILL 铁律/门的升格（留勘误注），其余留 X 节；**不选 b**
（多处同步违背修订传导纪律）。

## 决策三：时效敏感规格的登记形态

背景：平台尺寸/格式支持/商店规格/墨量上限随时间漂移（本轮实证：旧摘要的 LinkedIn
封面数已过时）。

- **选项 a：存"当期值+as-of 日期"**。优点：查库即得。缺点：**腐蚀性**——半年后库里
  是错的，且没有机制强制发现；与"静默失败"家族同构。
- **选项 b：只存"核对动作"规则**（"交付前现查当期规格页"），不存数值。
  优点：永不腐蚀。缺点：每次任务都要现查（多一步网络依赖）；丢掉了"大致量级"的
  快速参考价值（1080×1080 这类十年不变的主干数其实很稳定）。
- **选项 c：混合分层**——稳定主干（如"方图 1080×1080"级别、富黑配方）作为**候选
  数值**登记并标 `as-of:2026-05`；交付判据永远是"**交付前以当期官方规格页核对**"
  （红线级，进清单项）。库里的数值只是"预期值"，不作为交付依据。
- **配套**：数值条目带 `as-of` 日期与来源 URL，runner 可加"as-of 超 N 月标记陈旧"
  的软检查（待办，不预建）。

### 决策三默认建议：**选项 c**（与本轮 CR-C-11/CR-X-09 已写的形态一致——即当前
底稿已经按 c 落地，裁决只是追认）。

## 决策四：争议条目的登记形态

背景：4 处社区无共识（FS/D&B 先后、WB vs 曝光、墨量数值、锐化收尾形态）。

- **选项 a：不登记**，只等实战裁决。缺点：丢掉已知争议——实战撞上时 agent 无预警。
- **选项 b：只登"此处有争议"**，不登任何一派内容。优点：安全。缺点：丢掉两派的
  具体主张（有主张才有实战验证的对象）。
- **选项 c：两派并列登记，各带派系标注与出处，状态恒为"候选"，禁止升清单项**
  ——除非本机实战给出倾向证据（≥2 次同一倾向）。CR-A-04/04a 已经按此形态落地
  （04=冲突事实，04a=Woloszynowicz 派完整主张）。
- **红线（不论选哪个）**：争议条目永不被重排步当作"结论"呈现；开工消息若引用
  争议条目，必须向用户明示"此处无社区共识，我按 X 派尝试，可换向"——与门 G1
  （用户裁决）衔接。

### 决策四默认建议：**选项 c**（当前底稿已按 c 落地，裁决追认）。
