# 决策日志：与规划书/母框架的偏离点及理由（ps-mcp 建包日 2026-09-19）

规划书 = `_SKILL规划书_PS版.md`；母框架 = `_SKILL框架_达芬奇迁移版.md`。规划书 §六 A4
要求对规划书本身执行怀疑-裁决，偏离落账本文件。每条：原样 → 实际 → 为什么。

## D1 displayDialogs 分层：操作期弹窗抑制 ≠ 启动期模态防线

规划书风险 2 与第一铁律把 `app.displayDialogs = DialogModes.NO` 定为"模态弹窗卡死之源"
的对策【△待复核】。实测修订：displayDialogs 只抑制**脚本运行中**的操作弹窗；PS **启动期**
模态（本机实测=「暂存盘空间不足」警告）出现在任何脚本之前，displayDialogs 管不到，且
**直接阻塞 COM 类厂激活**（0x80080005，8 次重试 3 分钟不变；WM_CLOSE 弹窗后 0.0s 即连上，
证据链见 docs/research §2）。→ 连接 SOP 增加独立步骤"启动模态扫描"（01 分册 §2），
displayDialogs 保留为操作期防线（SKILL 铁律 6）。一行代码防不了两类弹窗——这是规划书
预写结论被机器现实修订的第一个实例（A1 应验）。

## D2 生态断言修订：官方 MCP 已存在，但走云端

规划书生态段（§二，2026-09-19 网调）写"无官方 Adobe MCP"。当日复核推翻字面：Adobe
"for Creativity" 官方连接器 2026-04-28 发布（50+ 工具接入 Claude）——但基于 Adobe 云
API，**不驱动本机桌面应用**；另有 Creative Agent 内置 PS 桌面版（对话式编辑）。
→ 定位裁决：本 skill 与官方连接器互补不冲突（官方=云生成管线；本 skill=本机安装版
脚本级细粒度控制）。生态段按此更新，检索日期入底稿（A2 应验：按月变的版图差点按旧
地图开工）。

## D3 通道定案：COM=S 主通道（实测确认），JSX 文件总线=F 兜底【✗待实测】

规划书列 COM/文件总线/UXP 三候选，"开工实测后定主次，不预写结论"。实测裁决：COM 全
生命周期通（连接/DoJavaScript/建档导出/Quit）→ **S 模式主通道=COM DoJavaScript**；
JSX 文件总线定为 F 兜底（通道无关、最笨最稳），全链路【✗待实测】台账 F-3；UXP 内嵌
不启用（需 UXP Developer Tool，本机未装；COM 已通则无必要），保留为借鉴
（batchPlay 用法）与远期候选。

## D4 激活态闸门判据：运营级证据替代显式查询

规划书闸门"订阅激活态（未登录则全停）"预设了可判定的激活态。实测：PS 无许可状态的
脚本 API（研究底稿 §1），无法显式机读。→ 判据改为**运营级**：建档→编辑→导出→关闭
全链路成功且无许可模态 = 视为激活（当日实测通过）；连接 SOP 的探针本身即是激活态
测试。声明形态：激活态永远以"当日探针通过"表述，不做跨日绝对化断言（台账纪律）。

## D5 模态框处置工具链：WM_CLOSE + 截图坐标，UIA 按钮定位不可靠

母框架 A7"GUI 自动化不可靠处人机分工明示"。实测落地：PS 自绘对话框（DroverLord/
OS_ViewContainer）在 UIA 树下**无按钮元素**，SendKeys Enter 无效。→ 弹窗处置 SOP：
先 WM_CLOSE（警告类弹窗等价于确认）；无效则 PrintWindow 截图人工辨认按钮坐标点击；
再无效则**明确请用户手点**（A7 边界，不许静默假装能自动）。探针脚本入 scripts/。

## D6 "MCP"是家族命名，不是传输承诺

照达芬奇 D3 惯例：本包 v0.1.0 无 MCP 服务器——S 模式走 COM DoJavaScript 直连，F 模式
走文件总线。社区确有 Photoshop MCP 服务器（loonghao COM 系 / mikechambers UXP 系）
但它们包装的正是这两个通道；skill 是知识包不是安装包，不引第三方依赖，方案写进
INSTALL/研究底稿指路。命名 ps-mcp 维持系列一致性。

## D7 治理层复用达芬奇 runner，指纹首日 14 条

规划书 §三"达芬奇 runner 可直接改包名复用"——照做（run-regression-checks.py 改
标记串与版本锚），四查语义与 exit code 逐项保持同族一致。指纹规模：14 条（全部锚
铁律/模式判定/门判据/留白声明等硬不变量），每条 grep 验证锚文件唯一后入表，
--self-test 反向实测首跑即跑（A6：新工具先拿自己跑，首跑抓自己 bug 是预期行为）。

## D8 暂存盘闸门处置边界：报告与等待，不代用户清盘

实测触发暂存盘空间警告（C: 22GB < 推荐值，台账 F-2）。处置裁决：**不动用户磁盘**——
清理 C 盘、改暂存盘偏好都属用户决策（后者若证实可脚本化再升级为 agent 代处置，
研究底稿待实测 #4）；agent 侧只做三件事：报告事实、每次连接自检时扫该模态、
WM_CLOSE 临时关闭让会话可继续。降级路径与主路径同级（A5）：模态在场 ≠ 停工，
= 扫描-关闭-继续。

## D9 输入端路由先于两段式；档位语义按分支分写（0.2.0）

规划书/母框架的 intake=两段式（先有什么/再要什么）+ 修图深度档（轻修/标准/合成级）。
实际增加**第 0 步用途分支判定**（8 分支：A 修图/B 合成/C 设计/D 切图/E 批处理/
F 绘画/G AI 生成/H 边界，依据 docs/research-use-case-branches-20260919.md），且档位
语义不再全分支通用。为什么：调研显示各分支的门配置、快照密度、agent 可代做边界差异
是结构性的（E 分支"首件试产走全门"、F 分支"不代画"、C 分支文字机验落地前限结构
操作、G 分支积分成本确认）——不先判分支，两段式会选错门与档，甚至静默接下不该接的
活（"帮我画"）。深度档（轻修/标准/合成级）保留为修图族语义，其他分支按各自等价
档位在 intake 声明；"不承接分支"一律明示并指路（3D→blender-mcp、剪辑→达芬奇、
RAW 编目→LR、矢量→Illustrator），与家族分工衔接。

## D10 社区两族评估：底层库实测通过，MCP 服务器不引入（0.3.0）

用户问"社区现成连接插件能不能用"。评估与实测：**COM 族**（Windows 系统级 COM 自动化，
PS 内零插件）底层库 photoshop-python-api 0.24.2 **本机实测通过**（PS 27.10 建档/关闭
全链路，`_probe/probe_pypshop.py`；其 Application 类在 `photoshop.api.application`，
README 示例已过时——纸面文档照例不可信）；其上的 MCP 服务器（uvx 即装即用）未经本机
实测（需 MCP 客户端环境）。**UXP 族**（进程内 UXP 面板+WebSocket+外部 MCP 服务器，
adb-mcp）安装链路重（UXP Developer Tool+开发者模式+面板在场），换进程内 batchPlay
全权限。裁决：两族 **MCP 服务器均不引入包内**（D6 立场维持——skill 是知识包不是安装包；
本 skill 的 S 模式就是 COM 族的同通道直连，引服务器=引入依赖漂移面）；使用建议写进
INSTALL（用户在 MCP 客户端自用场景：轻量选 loonghao 系、重装选 adb-mcp），定位=
它们是连接管道，本 skill 是管道之上的纪律/门/工艺层，可并存不冲突。

## D11 用户裁决：默认 ps-mcp（COM 直连），UXP 挂预留接口（0.4.0）

用户裁决原话："默认就用 ps-mcp，但是预留 UXP 接口"。落地：**默认通道=S 模式 COM
直连**（含 F 模式兜底不变）；**UXP 升格为预留第三通道**——在 01 分册 §6 挂出通道
契约（"通道可换，协议不变"：铁律/四门/report 投影/五段式/实看义务全部通道无关，
UXP 侧只换宿主与 batchPlay 能力面），并写明启用触发条件（F-9 实测证明必须进程内 /
工艺库确认需要描述符级能力 / COM 被环境禁用）与安全边界（自建面板＞临时借用
adb-mcp 只作验证；第三方代码不作常驻管道）。启用前置实测列 research §6 #15，
预留状态入台账 F-13。为什么这样落：预留=契约先行的空槽，不是代码占位——协议不变量
今天写死，未来启用时通道替换才不会腐化治理层；同时把"第三方 MCP 服务器不作默认
管道"从评估结论（D10）升格为裁决约束。

## D12 本地 LM Studio 集成：三级递进候选取用 + 重排器角色边界（0.6.0）

用户问询触发（0.5.0 后）："重排是不是每次运行都排"→ 修正为**三级递进**：L1 建库
分层（P1 常读/P2 条件触发，一次性）、L2 任务型组合缓存（任务型首次出现时排一次即
固化复用——"排完可以用很久"）、L3 运行时重排只作兜底（新任务型/条件全不命中/池跨
200 条）。②用户自有本地 LM Studio（127.0.0.1:8080）。实测：在载 qwen3-reranker-4b
+ text-embedding-qwen3-embedding-8b（4096 维）+ 多 LLM；**`/v1/rerank` 端点不存在**
→ 走 chat completions yes/no 判定式（system 需 `/no_think` 前缀，max_tokens=200，
并发偶发 HTTP 500 已加重试）。工具 `scripts/rerank_local.py`（stdlib、自噬通过）。
全矩阵校准（34 候选×任务型剖面=120 对）产出**重排器角色边界实证**：强于条件归属
（P2 桶精准命中），对 meta 规则全 0（X 节）且漏检批处理/G 分支措辞——因此 **P1 由
治理指定、P2 由重排器建议+人工确认、L3 输出仅参考**（机器建议人工裁决）。边界：
本地模型只排序不决定晋升；可选依赖（Server 未开时 L3 由 agent 内判断兜底，不阻塞，
F-14）；隐私红利=任务描述与工艺条目不出本机。校准报告：docs/craft-research/
p1p2-calibration-20260919.md。

## D13 视觉公理：多模态能力深度融合进每一层（0.7.0，用户裁决）

用户裁决原话："必须以模型有原生多模态能力为前提，深度融入每一个流程，开头的具体
识别，过程的实时检查修正，思考，成品的检验展示，知识库能力的识别与启动"。触发=
grid 任务 v1 的 G1 被拒——实证质量判定曾建立在降采样视图上（多模态用得不足，
F-16）。落地（感知通道地位=第一类公民，不是验收附件）：

1. **铁律 8**：视觉实看贯穿全流程，判定分辨率不足=没看（每阶段定义看什么/多大
   分辨率/判什么；证据=瓦片文件+实看清单入 report）；
2. **门改造**：G0 增视觉首察（视觉发现清单驱动方案假设）；新增 **Px 过程检查点**
   （每写操作后就地 1:1 实看-修正循环，02 分册 §7）；G3 增成品视觉检验（全长瓦片，
   CL-X-08）；G4 增展示包；
3. **分辨率纪律**：质量判定必须在缺陷可见的分辨率上做出；降采样视图只作导航；
4. **知识库识别与启动**：工艺条目带**核（视觉核验点）**字段——条目驱动的操作自动
   调度感知（看什么/多大倍率/判什么/异常信号），检查计划随宣告行留痕；
5. **双通道证据**：实看清单与文件系统互证，治理层可机查"是否真看过"。

为什么是公理不是条款：多模态不是流程中的一个步骤，而是**感知前提**——母框架
"凡依赖专家内在能力之处一律外置为可治理结构"在视觉域的对应物=把"看"外置为
可调度的检查计划+可机查的证据链。
